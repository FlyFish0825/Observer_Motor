# Observer_Motor 固定节点 CAN FD 电机协议

本文档对应当前 APP 固件。网络中节点号固定为 1～8，由上位机预先配置；APP 不提供节点发现、注册或动态分配功能。

> 当前测试配置：仲裁段和数据段均为 1 Mbit/s，CAN FD 关闭 BRS；普通反馈已恢复为每节点约 100 Hz。将来切换到 8 Mbit/s 数据段时，需同步打开 BRS 并修改 FDCAN 数据段时序。

## 1. 总线参数

- 标准 11 位 CAN ID。
- 仲裁段：1 Mbit/s。
- CAN FD 数据段：测试阶段 1 Mbit/s，关闭 BRS；预留切换到 8 Mbit/s+BRS。
- 多字节整数：小端序。
- 调试帧温度单位：0.1 ℃；普通反馈温度使用独立的 -20～150 ℃ 无符号满量程编码；心跳温度为 1 ℃。
- 调试帧相电流、Id/Iq 单位：0.01 A；普通反馈母线电流使用独立的 0～10 A 无符号满量程编码。
- 电压单位：0.01 V。
- 转速单位：rpm，`int16_t`。
- CAN 控制帧使用 `0x100`，所有节点同时接收。
- 不使用应用层 CRC；CAN FD 帧自身已经包含 CRC。Bootloader 管理帧仍保留原来的 CRC8。

## 2. 固定 ID 分配

| ID | 方向 | 含义 | 长度 |
|---:|:---:|---|---:|
| `0x000` | 上位机 → 节点 | APP 进入 Bootloader | 8 字节经典 CAN |
| `0x100` | 上位机 → 全部节点 | 速度/运行/调试控制 | 24 字节 CAN FD |
| `0x180 + NodeID` | 节点 → 上位机 | ENTER_BOOT 接收确认 | 8 字节经典 CAN |
| `0x200 + NodeID` | 节点 → 上位机 | 普通运行反馈 | 12 字节 CAN FD |
| `0x280 + NodeID` | 节点 → 上位机 | 在线心跳 | 8 字节经典 CAN |
| `0x300 + NodeID` | 节点 → 上位机 | 原实时调试反馈（不变） | 64 字节 CAN FD |
| `0x340 + NodeID` | 节点 → 上位机 | 参数辨识事件与结果，按需一次性反馈 | 64 字节 CAN FD |
| `0x380 + NodeID` | 节点 → 上位机 | APP 上电 HELLO（仅一次） | 8 字节经典 CAN |

例如 Node1 的普通反馈 ID 是 `0x201`，Node8 是 `0x208`。

## 3. 广播控制帧 `0x100`

固定 24 字节 CAN FD 数据，测试阶段关闭 BRS，字段如下：

为兼容现有调试工具，固件仍兼容旧版 `0x100` 经典 CAN 8 字节 RUN/SET_SPEED 帧；新上位机请使用下面的 24 字节广播帧。

| Byte | 字段 | 说明 |
|---:|---|---|
| 0 | Version | 当前为 `0x01` |
| 1 | Command | 命令码 |
| 2 | NodeMask | bit0～bit7 对应 Node1～Node8 |
| 3 | RunMask / Action | `0x10/0x11`时仍是RunMask；仅`Command=0x40`时解释为辨识Action |
| 4～5 | Sequence | 上位机递增序号，当前固件不强制连续 |
| 6～7 | Flags | 保留，发送 `0` |
| 8～9 | Speed1 | Node1 速度，`int16_t`，rpm |
| 10～11 | Speed2 | Node2 速度，`int16_t`，rpm |
| 12～13 | Speed3 | Node3 速度，`int16_t`，rpm |
| 14～15 | Speed4 | Node4 速度，`int16_t`，rpm |
| 16～17 | Speed5 | Node5 速度，`int16_t`，rpm |
| 18～19 | Speed6 | Node6 速度，`int16_t`，rpm |
| 20～21 | Speed7 | Node7 速度，`int16_t`，rpm |
| 22～23 | Speed8 | Node8 速度，`int16_t`，rpm |

速度有效范围为 `-10000～10000 rpm`；超出范围时，该节点不更新速度，也不执行同一帧中的启动请求。

### 命令码

| Command | 名称 | 行为 |
|---:|---|---|
| `0x10` | SPEED_VECTOR | `NodeMask`选中的节点更新各自速度；`RunMask`对应位为 1 时启动 |
| `0x11` | RUN_VECTOR | 使用 `RunMask`同时启停选中的节点 |
| `0x20` | DEBUG_SELECT | `NodeMask`只能选一个调试节点；Byte3 非零启用，Byte3 为零关闭 |
| `0x30` | STATUS_ONCE | `NodeMask`选中的节点立即发送一帧普通反馈 |
| `0x40` | CALIBRATION | `NodeMask`指定辨识节点，Byte3指定Action；状态与结果由`0x340+NodeID`返回 |

未选中的节点忽略 `0x10/0x11/0x30`，但所有节点都会执行 `0x20`，从而保证切换调试节点时旧节点退出调试模式。
`DEBUG_SELECT`的掩码必须是单 bit；空掩码、多 bit 掩码或 Byte3=0 都会关闭调试模式并恢复普通反馈。

### 参数辨识命令（Command = `0x40`）

复用本节同一条标准ID `0x100`、24字节CAN FD控制帧（BRS关闭），不添加第二套接收协议。Byte0=`0x01`，Byte1=`0x40`，Byte2=`NodeMask`，Byte3改为下表的Action，Byte4～5为小端请求序号；Byte6～23必须全为0，非零请求会拒绝。仅`0x40`改变Byte3的含义，旧的转速/启停命令仍按原RunMask解释。

| Action（Byte3） | 作用 | 结果判定 |
|---:|---|---|
| `0x01` | 完整Rs：AB→BC→CA | 三条线间及三个相电阻、平均Rs有效 |
| `0x02` | 完整Ls：AB→BC→CA | 三组Ls均有效；使用当前RAM中的Rs补偿 |
| `0x03` | 单组Ls AB | 仅重新测量AB |
| `0x04` | 单组Ls BC | 仅重新测量BC |
| `0x05` | 单组Ls CA | 仅重新测量CA |
| `0x06` | 停止辨识 | 取消当前序列、快速关断并完成外设恢复；不会停止无关的正常运行 |
| `0x07` | 读取RAM结果 | 不启动PWM，立即返回当前结果快照和有效位 |
| **`0x08`** | **连续Rs→完整Ls** | Rs成功且恢复外设后才启动Ls；全程成功才返回完整完成事件 |

启动类Action（`0x01～0x05`及`0x08`）要求NodeMask恰好一个bit；例如Node1为`01`、Node2为`02`。不允许一帧启动多个电机同时辨识。`0x06`停止和`0x07`读取可选择多个节点，每个命中节点用自己的返回ID及同一请求序号答复。NodeMask为0时忽略。

**安全与执行：** 命令在现有RX中断入队、由`MotorProtocol_Process()`在主循环执行，沿用已有串口/按键的Rs/Ls算法、ADC保护及`MotorCalibration_Stop()`，不在FDCAN中断里操作桥臂。启动前检查电机IDLE、ADC校零、母线5～50V及功率输出关闭；Ls还要求有效Rs与外设空闲。`0x08`的Rs完成后先留一个主循环轮次处理停止请求，再启动Ls。辨识过程中普通CAN启动命令不能抢占待续的Ls；停机命令可以取消辨识。结果只保存在RAM，不写Flash。

Node1连续辨识例子（`Sequence=0x0001`）：

```text
ID=0x100，CAN FD，DLC=24，BRS=OFF：
01 40 01 08 01 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

接收该命令后，先观察Node1的`0x341`接受事件，再观察Rs阶段完成事件以及最终成功/失败事件；不能把接受事件当成整个辨识已经完成。

### 控制示例

以下示例设置 Node1=1000 rpm、Node2=-1500 rpm、Node3=3000 rpm，其他节点不修改，并启动前三个节点：

```text
ID 0x100，DLC 24，数据：
01 10 07 07 01 00 00 00 E8 03 24 FA B8 0B 00 00 00 00 00 00 00 00 00 00
```

停止 Node2：发送 `Command=0x11`、`NodeMask=0x02`、`RunMask=0x00`，其余字节置零。

## 4. 普通反馈 `0x200 + NodeID`

每个节点默认约 100 Hz 发送一帧，使用 12 字节 CAN FD、BRS关闭。参考速度不上传，只发送实际状态。

| Byte | 类型 | 内容 |
|---:|---|---|
| 0～1 | `int16_t` | 实际机械转速，rpm |
| 2～3 | `uint16_t` | 估算母线电流，0～10 A 对应 0～65535（约 0.0001526 A/LSB） |
| 4～5 | `uint16_t` | 母线电压，0.01 V/LSB |
| 6～7 | `uint16_t` | STM32G431 内部温度，-20～150 ℃ 对应 0～65535（约 0.002594 ℃/LSB） |
| 8 | `uint8_t` | 电机状态：0=IDLE，1=OPEN_LOOP，2=CLOSED_LOOP |
| 9 | 位标志 | bit0=电流校准完成，bit1=速度环启用，bit2=电压限幅 |
| 10 | `uint8_t` | 反馈序号 |
| 11 | `uint8_t` | 保留，当前为 0 |

母线电流不增加独立ADC采样，FOC每周期按 `Pe = 1.5 × (Vd × Id + Vq × Iq)`、`Ibus_est = Pe / Vbus` 估算，并按 `Ibus_filter = 0.95 × old + 0.05 × new` 滤波。Byte2～3 的解码公式为 `Ibus(A) = raw × 10 / 65535`；负估算值钳为 0 A，超过 10 A 钳为 10 A。当母线电压不高于 0.1 V 时估算值按 0 A 处理。温度是 MCU 内部温度传感器的芯片温度，不是 PCB 外部 NTC 温度；普通反馈 Byte6～7 的解码公式为 `Temperature(℃) = raw × 170 / 65535 - 20`，低于 -20 ℃ 和高于 150 ℃ 的值分别钳为量程两端。ADC1 规则组每 10 ms 更新一次母线电压和内部温度，电流注入组不参与温度采样。

## 5. 调试反馈 `0x300 + NodeID`

只有 `DEBUG_SELECT` 选中的节点发送调试帧，周期约 5 ms（200 Hz，TIM6 时隙每 2 拍发送一帧）。进入调试后，其余节点停止普通反馈，只保留每秒心跳。调试帧 64 字节，主要字段如下：

| Byte | 内容 | 单位 |
|---:|---|---|
| 0～1 | 实际转速 | rpm |
| 2～3 | PLL电角速度 | 1 rad/s |
| 4～9 | 三相电流 Iu/Iv/Iw | 0.01 A |
| 10～13 | Id/Iq | 0.01 A |
| 14～17 | Ud/Uq | 0.01 V |
| 18～19 | 母线电压 | 0.01 V |
| 20～21 | MCU 温度 | 0.1 ℃ |
| 22～23 | 观测器电角度 | 0.01° |
| 24 | 电机状态 | 同普通反馈 |
| 25～27 | 状态标志 | 校准、速度环、电压限幅 |
| 28 | 反馈序号 | 递增 |
| 29～63 | 保留 | 当前为 0 |

控制帧始终优先于反馈帧。调度使用 TIM6 的 1 MHz 计数基准，每 1 ms 一个硬件时隙，共 10 个时隙循环，节点按 NodeID（1～8 对应时隙 0～7）固定错开发送普通反馈，不使用软件延时；调试帧在选中节点自己的时隙上每 2 拍发送一帧。

## 5.1 参数辨识结果 `0x340 + NodeID`

**新增独立的64字节CAN FD反馈，原`0x300+NodeID`实时调试布局、DEBUG_SELECT逻辑、200Hz时隙均不变。** 本帧不依赖DEBUG_SELECT：接收到辨识命令，命中节点即可单独返回。与现有协议一样使用标准11位ID、数据小端、BRS关闭，不增加应用层CRC。

例如Node1=`0x341`、Node8=`0x348`。本反馈为事件驱动，**不周期发送**；接收时要同时看事件类型及请求序号，不能以收到任何一帧就判为辨识成功。

| 字节 | 类型 | 定义 |
|---|---|---|
| 0 | uint8 | 版本，`0x01` |
| 1 | uint8 | 实际NodeID（1～8） |
| 2 | uint8 | Event，见下表 |
| 3 | uint8 | 原请求Action（`0x01～0x08`） |
| 4 | uint8 | Stage：0=空闲，1=Rs，2=Ls，3=Rs已完成、下一轮待启动Ls |
| 5 | uint8 | 当前/最后回路：0=AB，1=BC，2=CA |
| 6 | uint8 | Error，见下表 |
| 7 | uint8 | Valid：bit0=整套Rs有效，bit1=Ls AB，bit2=Ls BC，bit3=Ls CA |
| 8～9 | uint16 | 原控制帧Byte4～5请求序号，小端 |
| 10 | uint8 | 底层Ls原因：0正常；1过流、2 ADC/DMA、3超时、5时序、6双沿拟合无效 |
| 11 | uint8 | 保留，0 |
| 12～15 | float32 | 平均相电阻Rs，Ω |
| 16～19 | float32 | 线间电阻R_AB，Ω |
| 20～23 | float32 | 线间电阻R_BC，Ω |
| 24～27 | float32 | 线间电阻R_CA，Ω |
| 28～31 | float32 | 相电阻R_A，Ω |
| 32～35 | float32 | 相电阻R_B，Ω |
| 36～39 | float32 | 相电阻R_C，Ω |
| 40～43 | float32 | 相电感Ls_AB，**μH** |
| 44～47 | float32 | 相电感Ls_BC，**μH** |
| 48～51 | float32 | 相电感Ls_CA，**μH** |
| 52～63 | — | 保留，全部0 |

`float32`为IEEE754小端编码。Valid bit0只有全部线间电阻、全部相电阻和Rs均为正数才置位；bit1～3分别表示对应电感已有效。未完成的字段可能为0或旧RAM值，**必须以Valid判断是否可用**。单组Ls重新测量成功启动后，先清本组旧值，不会把旧结果误作本次完成。

| Event（Byte2） | 含义 | 后续行为 |
|---:|---|---|
| `0x01` | ACCEPTED，命令已受理并启动 | **不是成功结果**，还要继续等待 |
| `0x02` | COMPLETED，完整目标已完成 | 查看Valid与请求Action；连续模式需Rs和三组Ls全有效 |
| `0x03` | REJECTED，拒绝命令 | 不开始本次辨识 |
| `0x04` | FAILED，测量故障/结果无效 | 停止后续回路，保留已有效RAM数据 |
| `0x05` | STOPPED，当前任务被停止 | 原任务的Sequence随此事件返回 |
| `0x06` | SNAPSHOT，响应`0x07`读结果 | 仅表示返回了当前RAM快照 |
| `0x07` | RS_DONE，`0x08`的Rs阶段完成 | 已准备进入Ls，但连续任务尚未完成 |

| Error（Byte6） | 含义 |
|---:|---|
| 0 | 无错误 |
| 1 | 不支持的Action |
| 2 | 启动命令NodeMask不是单bit |
| 3 | 电机或已有辨识任务忙 |
| 4 | 未校零、母线异常、MOE开启或Ls缺少Rs |
| 5 | 启动ADC/DMA/定时器等资源失败 |
| 6 | 计算结果无效 |
| 7 | 主动停止/任务被取消 |
| 8 | 实时过流或ADC/DMA/时序等故障（详细原因见Byte10） |
| 9 | 预留字段Byte6～23非零，帧格式非法 |

收到`0x06`停止命令后，若有正在执行的CAN辨识任务，会先用**原Action、原Sequence**发`STOPPED`，再用停止命令的Action=`0x06`和它自己的Sequence发`COMPLETED`。若此前无CAN辨识任务，停止动作仍会答复，但不会中断正常运行中的FOC。

**发送策略与异常处理：** 新反馈沿用现有`MotorProtocol_Send()`；主循环保存最多4帧事件快照，在`MotorProtocol_Process()`入口和出口各非阻塞尝试发送一次，FDCAN FIFO忙则保留队首下轮重试，不从实时中断发送。活动任务始终预留两个事件槽，确保终态或停止操作的双回执不会被普通读取请求挤掉。若软件事件槽不足，新命令不执行、无法立即回执，上位机应限制未完成请求数并使用Sequence做超时重试；重复发送请求不具有自动去重语义。原`0x300`高速调试帧、TIM6时隙、普通反馈和每秒心跳均不因本功能改变。

## 6. 心跳 `0x280 + NodeID`

每个节点每秒发送一次 8 字节经典 CAN 心跳，不用于发现节点，只用于在线和状态监视。

| Byte | 内容 |
|---:|---|
| 0 | NodeID |
| 1 | 电机状态 |
| 2 | 电流校准完成：0/1 |
| 3 | 调试模式：0/1 |
| 4 | MCU 温度，`int8_t`，整数 ℃ |
| 5 | 电压限幅：0/1 |
| 6 | 当前反馈序号 |
| 7 | CRC8 |

CRC8 参数：Poly=`0x07`、Init=`0x00`、无反射、XorOut=`0x00`。

## 6.1 APP 上电 HELLO `0x380 + NodeID`

APP 初始化 FDCAN 后、启动周期 CAN FD 反馈前，先发送一次 8 字节经典 CAN HELLO，并最多等待 10 ms 确认其实际发送完成。发送失败或总线无应答不会阻塞电机主循环。此帧仅用于区分“APP 已运行且经典 CAN 可通信”和“后续 CAN FD 反馈异常”，不替代每秒一次的在线心跳。

| Byte | 内容 |
|---:|---|
| 0～4 | ASCII `HELLO`，即 `48 45 4C 4C 4F` |
| 5 | NodeID，范围 1～8 |
| 6 | 协议版本，当前 `0x01` |
| 7 | 前 7 字节的 CRC8，参数同心跳 |

例如 Node1 上电后应出现 `ID=0x381`、经典 CAN、DLC=8、数据 `48 45 4C 4C 4F 01 01 AA`。如果只看到 HELLO，随后收不到 `0x201`，应重点检查网关和分析仪是否支持当前 1 Mbit/s、关闭BRS的 CAN FD 反馈。

## 7. 进入 Bootloader

保留原有管理帧，发送经典 CAN：

```text
ID 0x000，数据：01 04 00 00 00 00 00 7B
```

APP 布局固件收到后关闭 PWM，写入备份寄存器请求标志并软件复位；Bootloader 消费标志后停留在 Bootloader。Standalone 布局不执行跳转。

Boot 布局 APP 校验节点号、命令和 CRC8 后，先关闭 PWM 并发送接收确认。Node1 的确认帧为：

```text
ID 0x181，经典 CAN，DLC 8，数据：01 04 01 00 00 00 00 19
```

Byte0 为实际节点号，Byte1 为 `ENTER_BOOT(0x04)`，Byte2 为 `0x01`（已接受），Byte7 为前 7 字节的 CRC8。APP 短暂等待确认帧发送完成，然后写入 `BKP0R` 并复位；等待发送队列空位和等待实际发出的两个阶段各设有 20 ms 超时，总线异常时也不会一直卡在 APP。此确认只证明 APP 收到了命令，不证明 Bootloader 已成功启动；Bootloader 是否停留仍以随后 `GET_VERSION` 的 `0x500 + NodeID` 应答为准。
## 9. 带宽预算（1 Mbit/s，当前测试配置）

| 项目 | 帧 | 频率 | 单节点带宽 | 8 节点合计 |
|---|---|---:|---:|---:|
| 普通反馈 | FD 12 B | 100 Hz | ≈ 1.9 kbit/s | ≈ 15.4% 总线负载 |
| 心跳 | 经典 8 B | 1 Hz | ≈ 0.1 kbit/s | ≈ 0.7% |
| HELLO | 经典 8 B | 上电 1 次 | 可忽略 | 可忽略 |
| 广播控制 | FD 24 B | 上位机按需 | - | 与反馈错开 |

调试模式：单节点 200 Hz × 64 B FD ≈ 17% 总线负载，其余节点只发心跳，总负载仍低于 20%。控制帧由上位机触发，不与反馈同 ID 冲突；FD 帧在 1 Mbit/s 全速下传输 64 B 约 640 bit 时间（约 0.64 ms），小于 1 ms 时隙，不会跨时隙堆积。
