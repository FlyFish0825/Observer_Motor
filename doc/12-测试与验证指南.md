# 测试与验证指南（补充资料）

> 本文回答一个问题：**改完代码，怎么证明没坏？**
> 验证分四层——主机回归、静态校验、构建验证、台架实测。每一层都明确写出"能证明什么、不能证明什么"。
> 施工步骤与验收标准见[07 实施计划](07-完全实现实施计划.md)，启动行为见[08 启动修正](08-双向静止启动与平滑接管修正.md)，出问题见[故障排查手册](11-故障排查手册.md)。

---

## 1. 验证分层总览

| 层 | 手段 | 命令 | 覆盖范围 | 前置条件 | 耗时量级 | 结论强度 |
|---|---|---|---|---|---|---|
| 1 主机回归 | `tests/test_runtime_response.py` | `python tests/test_runtime_response.py` | 应用层状态机、参考仲裁、速度/接管数值行为、电流环 PI 抗饱和 | 本机有 `gcc` | 数秒 | 强：能证明状态/参考逻辑没回归 |
| 2 静态校验 | `tools/codecheck.py` | `python tools/codecheck.py <旧目录> <新目录>` | "本次改动只动了注释" | Git 中存在可比对的旧版本 | 毫秒级 | 强：能证明代码 token 流未变 |
| 3 构建验证 | CMake 预设 | `cmake --preset … && cmake --build --preset …` | 编译、链接、布局、产物生成 | arm-none-eabi 工具链、Ninja | 数十秒 | 中：能证明可编译可链接，不证明行为正确 |
| 4 台架实测 | 串口 + 示波器 + 真实电机 | 见 §6 | 真实电气与机械行为 | 硬件、限流电源、安全措施 | 分钟到小时 | 最强，但不可自动重复 |

**四层之间的关系是"倒金字塔"**：主机回归跑得最快、最容易重复，但它**替换掉了观测器和真实电机**；台架实测最可信，但每次都要动硬件。

## 2. 主机回归测试

### 2.1 它到底做了什么

`tests/test_runtime_response.py` 不是"另写一套模型"，而是**从真实源码里抠出函数**再编译：

1. 读取 `Core/Src/motor_app.c` 的**原文**。
2. 用正则从 `#define MOTOR_APP_CONTROL_HZ` 到 `} MotorApp_Startup_t;` 截取**常量区与结构体定义**（`tests/test_runtime_response.py:34`）。
3. 从真实源码里逐个抽取这 14 个**静态函数原文**（`:35`）：

   | # | 函数 | 作用 |
   |---|---|---|
   | 1 | `MotorApp_VirtualRpm` | 虚拟角 → 虚拟转速 |
   | 2 | `MotorApp_RpmToElectricalRad` | rpm → 电角速度 |
   | 3 | `MotorApp_SetOpenLoopTarget` | 设置 I/F 目标 |
   | 4 | `MotorApp_Slew` | 斜坡限速 |
   | 5 | `MotorApp_BeginForcedOpenLoop` | 进入强制开环 |
   | 6 | `MotorApp_ResolveControlReference` | 每拍控制参考仲裁 |
   | 7 | `MotorApp_ControlSpeedFeedback` | 速度控制反馈滤波 |
   | 8 | `MotorApp_UpdateObserverReady` | ObserverReady 判据 |
   | 9 | `MotorApp_BeginObserverHandover` | 进入接管 |
   | 10 | `MotorApp_ObserverIsFinite` | 观测器有限性检查 |
   | 11 | `MotorApp_RecoverAuxObserver` | 辅助观测器恢复 |
   | 12 | `MotorApp_AdvanceStateMachine` | 状态机推进 |
   | 13 | `MotorApp_UpdateStateTransition` | 状态切换判定 |
   | 14 | `MotorApp_StartupPhaseCode` | 相位码 |

4. 把 `tests/runtime_host_prelude.h` + 常量区 + `tests/runtime_host_state.h` + 上述函数 + `tests/runtime_host_cases.c` 拼成 `build/runtime_response_tests/runtime.c`。
5. **真实编译 `Core/Src/controller.c`**（不是替身），链接进同一个可执行文件。
6. 在 `-O0`、`-O2`、`-O3` 三档优化下各跑一遍（`:52`）。

编译参数（`:54`）：

```
gcc -std=c11 <-O0|-O2|-O3> -Wall -Wextra -Werror \
    -I tests/host -I Core/Inc \
    build/runtime_response_tests/runtime.c Core/Src/controller.c -lm -o runtime_<opt>.exe
```

### 2.2 被替换掉的部件（关键认知）

`tests/runtime_host_prelude.h` 提供的是**替身**，不是真实现：

| 被替换 | 替身行为 | 后果 |
|---|---|---|
| `Observer_Run()` | **空函数**，什么都不做（`prelude.h:23`） | 磁链积分、atan2、PLL **完全没有被测** |
| `Observer_Init()` | 只做字段拷贝与 PLL 初始化（`:24`） | 观测器内部动态未测 |
| `MotorApp_SinCos()` | 用 `sinf/cosf` 代替 CORDIC | 硬件三角函数未测 |
| `FOC_WrapToPiFast()` | 主机版实现 | 与器件版实现可能有细节差异 |
| `TIM1`、`TIM` 寄存器 | 一个只有 `BDTR` 字段的结构体（`runtime_host_state.h:14`） | 所有寄存器级行为未测 |
| `MotorApp_EnterFault()` | 只置标志（`:18`） | 故障锁存/快照逻辑未测 |
| `arm_sqrt_f32()` | `tests/host/arm_math.h` 用 `sqrtf` 实现 | CMSIS-DSP 未测 |

`runtime_host_cases.c:42` 也明确写了：`/* Ideal current following: this is a reference/state test, not a motor model. */` —— **它是参考/状态测试，不是电机模型**。

### 2.3 怎么运行

工作目录是工程根目录：

~~~powershell
cd F:\file\BaiduSyncdisk\Project\Observer_Motor
python tests/test_runtime_response.py
~~~

- 依赖：本机 `gcc` 在 `PATH` 上（脚本用 `shutil.which('gcc')`，找不到就退出并提示 `Native gcc not found`）。
- 输出：控制台打印每一档优化的用例结果；汇总写入 `build/runtime_response_tests/results.log`。
- 生成物：`build/runtime_response_tests/runtime.c`（可人工阅读）、`runtime_0.exe` / `runtime_2.exe` / `runtime_3.exe`。
- 退出码：任何 `CHECK` 失败会 `exit(1)`，`subprocess.run(..., check=True)` 随之抛错。

### 2.5 失败时怎么读

失败输出格式（`runtime_host_cases.c:1`）：

```
FAIL line 155: NEAR(startup.if_iq_magnitude,4,0.00001f)
```

- `line` 是**用例文件**的行号，直接跳到 `tests/runtime_host_cases.c:155`。
- 三个优化档的失败应一致；**只有某一档失败**通常指向浮点优化差异或未初始化内存，而不是逻辑错误。
- 二分定位：把 `main()` 里的用例注释掉（临时改测试文件是允许的，它不属于固件），或先只跑 `-O0`。

## 3. 静态校验：`tools/codecheck.py`

### 3.1 原理

它比较两份 C 源码在**剥掉注释、字符串内容和全部空白**之后的 token 流：

- `//` 行注释与 `/* */` 块注释被整体删除；
- 字符串/字符字面量内容被抹掉（只保留引号类型），因此改注释里的文字、改字符串内容都不可见；
- 所有空白被删除，所以**行号偏移、缩进变化、换行重排都不会误报**。

只要 token 流一致，就证明"这次改动没有触及任何可执行代码"。

### 3.2 用法

~~~powershell
# 目录对目录：递归比较旧目录下所有 .c/.h/.cpp/.hpp/.s/.S
python tools/codecheck.py <旧版本目录> <新版本目录>

# 单文件对单文件
python tools/codecheck.py <旧文件> <新文件>
~~~

典型用法是配合 Git 取回旧版本：

~~~powershell
git worktree add ..\_old <某个提交>
python tools/codecheck.py ..\_old\Core Core
git worktree remove ..\_old
~~~

输出末行形如 `checked=31 code_changed=0 missing=0`；有差异时打印 `CODE CHANGED:` 与 unified diff（最多 120 行），退出码非 0。

### 3.3 什么时候会误报

| 情况 | 结果 | 说明 |
|---|---|---|
| 新增/删除文件 | `missing` 计数上升 | 目录对目录时必须保证新旧目录文件集合一致 |
| 改变字符串字面量内容 | **不报** | 字面量内容被抹掉，这是刻意的 |
| 把注释移进宏、或宏体里塞注释 | 可能报差异 | token 流里宏体注释本来就不参与比较 |
| 反斜杠续行被重排 | **不报** | 空白被删除 |
| 改了 `#if` 的表达式 | 会报 | 预处理器指令本身也是 token |
| 编码变化（UTF-8 BOM / GBK） | `errors='replace'` 兜底，可能产生差异 | 统一用 UTF-8 |

### 3.4 为什么它对"只改注释"的提交是必要的

本工程有过整批"只补中文注释"的提交。这类提交**无法用编译或测试证明它没动代码**——编译通过不代表语义没变。`codecheck.py` 用 token 流比对把这件事变成可验证的机械结论，是注释类改动的**唯一有效证据**。

## 4. 构建验证

### 4.1 四个预设

`CMakePresets.json` 定义了四个 configure/build 预设，均为 Ninja + `cmake/gcc-arm-none-eabi.cmake` 工具链：

| 预设 | `CMAKE_BUILD_TYPE` | `APP_LAYOUT` | `BOARD_HSE_HZ` | 链接地址 | 期望产物 |
|---|---|---|---|---|---|
| `Debug` | Debug | standalone | 默认 16 MHz | 0x08000000 | `build/Debug/Observer_standalone.bin` |
| `Release` | Release | standalone | 默认 16 MHz | 0x08000000 | `build/Release/Observer_standalone.bin` |
| `Boot-Release` | Release | boot | 默认 16 MHz | 0x08005000 | `build/Boot-Release/Observer_boot.bin` |
| `Boot-Release-HSE24` | Release | boot | 24000000 | 0x08005000 | `build/Boot-Release-HSE24/Observer_boot_hse24.bin` |

### 4.2 命令

~~~powershell
cd F:\file\BaiduSyncdisk\Project\Observer_Motor

cmake --preset Release
cmake --build --preset Release

cmake --build --preset Boot-Release-HSE24
~~~

### 4.3 期望的 Flash 占用

`doc/08-双向静止启动与平滑接管修正.md` 最后记录的实测值如下。**以最近一次实测为准**，这里只作为"量级是否合理"的参照：

| 配置 | Flash 占用 | 输出文件 |
|---|---:|---|
| Release | 72752 B | `build/Release/Observer_standalone.bin` |
| Debug | 102152 B | `build/Debug/Observer_standalone.bin` |
| Boot-Release | 73424 B | `build/Boot-Release/Observer_boot.bin` |
| Boot-Release-HSE24 | 73456 B | `build/Boot-Release-HSE24/Observer_boot_hse24.bin` |

同一次记录里 RAM 均为 7112 B。

### 4.4 怎样判断产物真的更新了

构建"成功"不等于产物是新的。至少核对一项：

1. **时间戳**：`Get-Item build\Release\Observer_standalone.bin | Select LastWriteTime`
2. **大小是否变化**：与上表对比；大小完全不变要警惕是否真的重新编译了。
3. **哈希**：`Get-FileHash build\Release\Observer_standalone.bin -Algorithm SHA256`
4. **`APP_FLASH_START` 是否生效**：Boot 版必须链接到 `0x08005000`，并用同一地址烧录。**不要把不同布局的镜像按同一地址烧录。**

### 4.5 构建验证不能证明什么

- 不能证明控制行为正确（状态机、观测器、PI 的数值正确性都不在编译范围内）。
- 不能证明布局与真实板卡一致（晶振、地址、Bootloader 是否存在都属于外部事实）。
- 不能证明实时性预算满足（`status` 的 `TIMING` 行才是运行时证据）。

## 5. 变更后的推荐顺序

改完代码，按这个顺序走，**每一步不过就不要进下一步**：

1. `python tools/codecheck.py <旧> <新>` ——如果本意只是改注释，这一步必须 0 差异。
2. `python tests/test_runtime_response.py` ——三档优化全过。
3. 四个预设全部构建（至少构建与本次改动相关的那个）。
4. 核对产物时间戳 / 哈希 / 布局地址。
5. 烧录 + 台架实测（§6）。
6. 记录实测数据，追加到 [08 启动修正](08-双向静止启动与平滑接管修正.md) 或 [07 实施计划](07-完全实现实施计划.md) 的实施记录。

## 6. 台架实测

每一步都写明：目的、安全条件、命令、采集、通过判据、失败回退。

> **总原则**：首次验证必须空载；上电串限流；手不离开断电开关。

### 步骤 0：上电与零偏校准确认

| 项 | 内容 |
|---|---|
| 目的 | 确认固件跑起来、控制中断在跑、校准完成 |
| 安全 | 母线仍可限流；电机空载 |
| 命令 | 观察上电提示 `READY: set run 1 / set run 0 / status`，然后 `status` |
| 采集 | `STATUS` 行的 `cal=` `adc_irq=` `MOE=` `adc_cfg=` |
| 通过判据 | `cal=1`；`adc_irq` 持续增长；`adc_cfg=1`；`MOE=0`（未启动时功率桥关闭） |
| 失败回退 | `adc_cfg=0` → 见[故障排查](11-故障排查手册.md#25-adc-注入配置自检失败起不来的最常见原因)；`adc_irq` 不涨 → 查 ADC 触发链路 |

### 步骤 1：定位（ALIGN）确认

| 项 | 内容 |
|---|---|
| 目的 | 确认固定角注入把转子拉到已知位置 |
| 命令 | `set wave_mode 1` + `set just_float 1`，再 `set speed 1500` + `set run 1` |
| 采集 | 波形模式 1；`status` 的 `START phase=` 与 `ctrl_rad` |
| 通过判据 | 进入 ALIGN 后 `ctrl_rad` 恒为 0 rad（alpha 轴）；30 ms 后离开 ALIGN |
| 失败回退 | 转子完全不动 → 查相序、`MOE`、定位电流 |

### 步骤 2：I/f 开环拖动确认

| 项 | 内容 |
|---|---|
| 目的 | 确认虚拟角按受限加速度爬升，电机跟随 |
| 命令 | 同步骤 1，观察 |
| 采集 | `set wave_mode 2`（电流跟踪七通道）；`status` 的 `START if_rpm=` `if_iq=` |
| 通过判据 | `if_rpm` 单调上升；相电流幅值约等于 `if_iq`；无堵转噪声 |
| 失败回退 | 爬不上去 → 增大 `MOTOR_APP_IF_IQ_A` 或减小加速度；抖动 → 查相序与参数 |

### 步骤 3：观测器可信判据建立

| 项 | 内容 |
|---|---|
| 目的 | 确认 ObserverReady 能持续成立 |
| 采集 | `status` 的 `rdy=` `rdy_fail=` `rdy_hist=` `rdy_count=` `rdy_max=` `span=`；`START dn=` |
| 通过判据 | `span` 累计到 ≥ 2π；`rdy_count` 连续增长到 30 ms 对应拍数；`rdy=1` |
| 失败回退 | 见 [故障排查 §3.2](11-故障排查手册.md#32-observerready-失败位图rdy_fail--rdy_hist--mask) |

### 步骤 4：平滑接管进入闭环

| 项 | 内容 |
|---|---|
| 目的 | 确认控制角从虚拟角平滑交给观测器 |
| 采集 | `startdiag` 的 `HANDOVER` 段与 `CLOSED` 段；`status` 的 `OBSERVER dtheta=` |
| 通过判据 | `HANDOVER` 与 `CLOSED` 都有快照（不是 `no snapshot`）；接管期间 `dtheta` 在负载角附近稳定，不持续增长 |
| 失败回退 | `fail=2`/`fail=7` → 见故障排查 §2.8 / §2.13 |

### 步骤 5：低速 1500 rpm 稳态

| 项 | 内容 |
|---|---|
| 命令 | `set speed 1500` + `set run 1`，稳定后 `status` |
| 采集 | `DRIVE rpm=` 与 `rpm_f=`；`CURRENT Iq_ref/Id/Iq/Ud/Uq/Ulim`；`CONTROL sat_d/sat_q/speed_aw` |
| 通过判据 | `rpm_f` 稳定在 1500 附近；`Id` 接近 0；`sat_q` 多为 0；`Ulim ≈ Vbus/√3` |
| 失败回退 | `Id` 偏大 → 角度不对齐；`sat_q` 长期非 0 → 电压不足或增益过高 |

### 步骤 6：升速到 3000 rpm 与降速

| 项 | 内容 |
|---|---|
| 命令 | `set speed 3000`，稳定后 `set speed 1500` |
| 采集 | `set wave_mode 3`；`status` 的 `DRIVE`、`CURRENT`、`OBSERVER weight=` |
| 通过判据 | 升速过程 `Iq_ref` 有界；`weight` 随转速从 1 向 0 过渡；降速不触发 fail |
| 失败回退 | 出现振动 → 见故障排查 §2.18 |

### 步骤 7：正反转切换（含 ±800 rpm 穿零）

| 项 | 内容 |
|---|---|
| 命令 | 在闭环下直接发反向目标，例如 `set speed -2500` |
| 采集 | `set wave_mode 3`；`status` 的 `CONTROL brake=`；`START phase=`（`12` 高速闭环制动 → `33` 低速强制 I/F → 接管） |
| 通过判据 | 高速段保持闭环制动；实际转速降到 ±800 rpm 才切 I/F；穿零过程中控制角连续积分、无跳角；`Iq_ref` 渐变不突加 |
| 失败回退 | 见故障排查 §2.18 |
| 备注 | 主机回归已覆盖这一路径的**状态与参考行为**，但它用的是合成观测与理想电流跟随，**不能替代这里的实测** |

### 步骤 8：高速闭环制动

| 项 | 内容 |
|---|---|
| 目的 | 确认高速下反向目标先制动而不是立刻切 I/F |
| 采集 | `status` 的 `brake=1`；`CURRENT Iq_ref` 为反向且幅值受控 |
| 通过判据 | 转速单调下降；母线电压不异常抬高；无过流 |
| 失败回退 | 母线回馈导致过压 → 降低制动电流或限制降速斜率 |

### 步骤 9：故障注入与保护验证

| 注入 | 期望 | 采集 |
|---|---|---|
| 给 0 或非法目标转速 | `fail=3`，安全停车 | `status` 的 `DRIVE cmd=`、`fail=` |
| 把 `vbus` 写成 0 | `Ulim=0`，`fail=8` 或电流环失去输出 | `CURRENT Ulim=`、`fail=` |
| 断开一相电流采样 | 相电流不平衡，`TRACK` 位置起 | `ADC` 行、`rdy_fail` |
| 降速到 0（`set speed 0`） | 停车、回到 IDLE、`MOE=0` | `STATUS` 行 |
| 故障闭锁后直接再 `set run 1` | **被忽略**，必须先 `set run 0` | 串口提示 `FAULT latched: …` |
| 反复 `set run 0` / `set run 1` | 无异常、无残留状态 | `STATUS` 行 |

> 注意：`MOTOR_APP_CLOSED_LOOP_HEALTH_ENABLE = 0`，**当前的闭环健康门限没有启用**。所以"高速电流误差过大"不会自动停机，故障注入里不要指望它触发 `fail=2`。

## 8. 已知的验证盲区

下面这些**主机回归无法证明**，必须靠实测或专用仪器：

1. **真实转子是否同步**：回归用合成观测角，只验证"给定已同步观测时状态机怎么走"。
2. **磁链观测器与 PLL 的真实精度**：`Observer_Run()` 在回归里是空函数。
3. **机械动力学**：没有惯量、摩擦、负载模型。转速在回归里是直接赋值的。
4. **推进器/负载振动是否消除**：`doc/08` 记录的那次修正**未烧录**，振动结论待实机波形验证。
5. **回调执行时间预算**：`TIMING` 行也明确标注 **HAL 中断入口开销未计入**，真实占用比它大。
6. **功率级非线性**：死区、开关损耗、母线跌落都不在模型里。
7. **端电压 RC 相位滞后**（100k/5.1k/68nF，`fc ≈ 482 Hz`）：仅在实机上体现。
8. **CAN/FDCAN 时序与总线负载**：需要抓包器。
9. **极端温度与电源波动**：需要环境试验。
