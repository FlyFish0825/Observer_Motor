# 代码走读路线图（补充资料）

> 本文给出一条**有顺序的读代码路线**：从哪读起、每个文件看什么、读到什么程度可以往下走。
> 它不重复源码本身（源码已有详细中文注释），也不重复逐符号签名（见[底层参考](05-底层参考.md)）。
> 建议配合 `doc/项目.html` 的源码查看器使用：点击任意函数引用可直接跳到实现。

---

## 1. 先建立三个认知

读代码之前，先记住三件事，能省掉大量困惑：

1. **有两个执行域。** 主循环（`while(1)`）和 ADC 控制中断（25 kHz）。绝大多数"为什么这个值会变"的问题，答案都是"另一个执行域改了它"。
2. **有一个唯一的控制目标入口。** 应用层每拍通过 `FOC_Control_SubmitReference()` 提交 `theta_ctrl` 与 dq 参考；控制器只读这个结构。启动/接管/换向**不允许**改控制器内部状态。
3. **时间基准只有两个。** 25 kHz 电流节拍（Ts = 40 µs）和 1 ms 通信节拍（TIM6）。速度环是 25 kHz ÷ 25 = 1 kHz。

---

## 2. 推荐路线（五段）

~~~text
第一段：入口与执行域      main.c → stm32g4xx_it.c → motor_app.h
第二段：实时控制主干      motor_app.c（中断入口）→ controller.h/c → observer.c → foc_math.c
第三段：采样与执行        adc.c → board_adc.c → opamp.c → tim.c → cordic.c
第四段：外部接口          debug_console.c → motor_protocol.c → usart.c → fdcan.c
第五段：构建与布局        app_memory.h → CMakeLists.txt → 链接脚本 → app_boot_control.c
~~~

## 3. 第一段：入口与执行域

### 3.1 `Core/Src/main.c`（278 行）

| 看什么 | 观察点 |
|---|---|
| `main()` 开头 | 第一句就是 `MotorApp_ForcePowerStageSafe()`——在任何 HAL 初始化之前把六路 PWM 引脚置低 |
| 初始化顺序 | `FOC_Data_Init()` → `MX_TIM1_Init()` → `MotorApp_Init()`。**这个顺序不能乱**：TIM1 初始化要读 `foc.timer` 里的 ARR、ADC 触发位置与死区 |
| `SystemClock_Config()` | 170 MHz 的来源；`BOARD_HSE_HZ` 如何参与 PLL（16 MHz → M=4，24 MHz → M=6） |
| `SCB->VTOR` | 设为 `APP_FLASH_START`，与链接地址一致 |
| `while(1)` | 只调用两个函数：先 `MotorProtocol_Process()`，再 `MotorApp_Process()` |
| USER CODE 4 区 | HAL 回调转发：`HAL_ADCEx_InjectedConvCpltCallback`、`HAL_UARTEx_RxEventCallback`、`HAL_UART_ErrorCallback`、`_write()` |

**读完应能回答**：上电到进主循环之间发生了什么？哪些动作必须在 HAL 初始化之前？

### 3.2 `Core/Src/stm32g4xx_it.c`（362 行）

| 看什么 | 观察点 |
|---|---|
| `ADC1_2_IRQHandler` | 实时控制的总入口；它调用 HAL 回调，回调再调到 `MotorApp_OnInjectedConversion()` |
| 其它中断 | UART DMA 事件、FDCAN 接收、TIM6 |
| 中断优先级 | 决定谁可以打断谁 |

**读完应能回答**：25 kHz 控制是从哪条链路进来的？CAN 接收会不会影响控制中断？

### 3.3 `Core/Inc/motor_app.h`（68 行）+ `Core/Inc/controller.h`（649 行，**必读**）

`motor_app.h` 很短，但注释点明了本模块是"唯一同时接触主循环域和 ADC 中断域的模块"。

`controller.h` 是整个工程**注释密度最高**的文件，值得完整读一遍。重点看：

| 看什么 | 为什么 |
|---|---|
| `PI_Controller_t` 注释段 | 区分"配置段（volatile）/ 历史状态段 / 输出段"三类的并发属性 |
| `FOC_Control_Reference_t` | 唯一控制目标入口，以及"**应用层若想用有限斜坡，必须在 SubmitReference 之后再写**"的顺序约定 |
| `FOC_Control_t` | 六个 volatile 外部命令字段与其余字段的区别 |
| `FOC_Control_Run()` 的 doc 注释 | 七步流程写得非常细：记录反馈 → 读仲裁使能 → 模式切换 → Iq 限速 → 电压限幅 → 电流环 → 回传 |
| 默认参数宏区 | 每个增益都写了量纲与整定依据 |

**读完应能回答**：为什么"进入速度模式"只在那一位从 0 变 1 的那一拍做无扰预装？`sample_time` 和 `ki` 为什么必须一起改？

## 4. 第二段：实时控制主干

### 4.1 `Core/Src/motor_app.c`（1884 行，**最大的文件**）

这是核心，建议**分四次读**：

**第一次：只看常量区（约 45~180 行）**
从 `MOTOR_APP_CONTROL_HZ` 到 ADC 注入序列期望值。这里集中了所有启动/接管/判据参数，每一条都有推导注释。读完这一区，启动行为的"设计意图"基本就清楚了。

**第二次：只看枚举与结构体（约 185~300 行）**
`MotorApp_Fail_t`（fail 码）、`MotorApp_ReadyFail_t`（12 位失败位图）、`MotorApp_WaveMode_t`（波形模式）、`MotorApp_Startup_t`（一次启动的全部中间状态，字段注释很全）。

**第三次：读中断入口 `MotorApp_OnInjectedConversion()`**
按顺序看：检查 ADC1 → 零偏校准累加 → 端电压融合 → Clarke/Park → `Observer_Run()` → 状态机推进 → `MotorApp_ResolveControlReference()` → `MotorApp_RunCurrentLoop()` → 写 CCR1~3 → 波形发送。
注意函数开头的时间预算注释：**单拍 40 µs，不得调用阻塞式 HAL**。

**第四次：读启动状态机的主干**
`MotorApp_StartControlSequence()` → `MotorApp_AdvanceStateMachine()` → `MotorApp_UpdateStateTransition()` → `MotorApp_BeginObserverHandover()`。
以及判据：`MotorApp_UpdateObserverReady()`。

**读完应能回答**：一个 run 请求从被接受，到电机进入闭环，中间经过哪些判定与多少拍？

### 4.2 `Core/Src/controller.c`（1210 行）

| 看什么 | 观察点 |
|---|---|
| `PI_Controller_RunError()` | 抗饱和的全部逻辑：先算积分候选 → 夹到积分限幅 → 合成未限幅输出 → 越界且误差同向则撤回积分 |
| `PI_Controller_PreloadOutput()` | 反算 `integral = desired_output - Kp*error`，这是无扰切换的数学核心 |
| `FOC_SlewSpeedReference()` | 阶跃 → 斜坡；注意 `0` 是冻结参考 |
| `FOC_Control_Run()` | 与头文件注释对照着读，看代码怎么落实那七步 |
| `FOC_Control_RotateCurrentIntegrals()` | 只搬"切换坐标系额外多出的那次旋转" |

**读完应能回答**：为什么这里的抗饱和"反向误差仍允许积分"？

### 4.3 `Core/Src/observer.c`（390 行）

| 看什么 | 观察点 |
|---|---|
| `Observer_Init()` | 初始磁链设为 alpha 轴正方向（与 ALIGN 的固定角 0 rad 对应，这是刻意的） |
| `Observer_Run()` 的积分 | `error = flux_linkage² - psi_mag²`，`correction = gain × error × psi`（径向非线性校正，只修幅值不修角度） |
| 磁链提取 | `psi = x - L*i` |
| `Observer_PLL_Run()` | 鉴相用磁链方向，`inv_psi_mag` 避免两次除法；`psi_valid` 决定本次是否更新 |
| 速度滤波器 | 两级一阶级联；头文件解释了为什么不用单节二阶巴特沃斯 |

**读完应能回答**：为什么磁链无效的拍里 `speed_rpm` 保持上一拍值？

### 4.4 `Core/Src/foc_math.c`（539 行）+ `Core/Inc/foc_math.h`（610 行）

| 看什么 | 观察点 |
|---|---|
| `FOC_Data_Init()` | 板级参数的唯一来源：PWM/死区/时钟、电流增益、电机参数、观测器配置 |
| 95% 重构阈值 | `foc_current_rebuild_threshold = pwm_arr * 95 / 100` |
| `FOC_PWM_Start()` / `FOC_PWM_Stop()` | 先设 50% 中点再开输出；停止时还要清母线电流估算 |
| `FOC_Get_Iabc()` | 零偏扣除、增益换算、高占空比时的 KCL 重构 |
| `FOC_SVPWM_Run()` | 共模注入；`duty = 0.5 + u/Vbus` 的由来 |
| `foc_math.h` 内联函数 | Clarke/Park/逆变换、`FOC_WrapToPiFast`、CORDIC 正余弦 |
| CORDIC | 为什么不用 HAL 包装 |

**读完应能回答**：为什么"三相占空比都为 50%"不等于"六个开关全关"？

## 5. 第三段：采样与执行

### 5.1 `Core/Src/adc.c`（492 行）

| 看什么 | 观察点 |
|---|---|
| 注入组配置 | ADC1 四个 Rank（Ia/Ic/U端/W端）、ADC2 两个 Rank（Ib/V端） |
| `ScanConvMode` | **重点**：设为 `DISABLE` 时 HAL 会静默截断注入序列（历史事故的根源） |
| 规则组配置 | 间断模式，每次软件触发一个 Rank：母线（PA0）与内部温度 |
| 采样时间 | 温度通道需要 247.5 周期，**顺序不能弄反** |

### 5.2 `Core/Src/board_adc.c`（60 行）+ `Core/Inc/board_adc.h`（52 行）

`board_adc.c` 只有 60 行、两个函数：`BoardAdc_Update()`（主循环阻塞式逐 Rank 轮询 ADC1 规则组，
成功就整体赋值给 `board_adc_measurements`）与 `BoardAdc_GetMeasurements()`（返回指针）。

值得注意的**不是**并发机制，而是它的**不存在**：源码注释与历史文档都提到 seqlock，
但当前代码里没有序号、没有快照读端，也没有 `BoardAdc_GetSnapshot()`——
规则组测量由主循环独占读写，控制中断只读注入组的值。

| 看什么 | 观察点 |
|---|---|
| `BoardAdc_Update()` | 只轮询 2 个 Rank（母线、温度）；失败不发布，保持上一轮 |
| `BoardAdc_GetMeasurements()` | 返回共享结构体地址，无拷贝、无校验 |
| 为什么中断不读它 | 中断需要的是电流与三相端电压，它们来自注入组 |

### 5.3 其它板级文件

| 文件 | 行数 | 看什么 |
|---|---|---|
| `Core/Src/opamp.c` | 251 | 三个独立 OPAMP 的配置；**代码配置不能替代外部硬件核对** |
| `Core/Src/tim.c` | 273 | TIM1 中心对齐 PWM、死区、CH4 触发点；TIM6 通信节拍 |
| `Core/Src/cordic.c` | 105 | 硬件三角函数配置与结果读取（CubeMX 生成） |
| `Core/Src/bsp_dwt.c` | 200 | DWT 周期计时与延时 |
| `Core/Src/dma.c` / `gpio.c` | 76 / 65 | DMA 通道与 GPIO 模式 |
| `Core/Src/usart.c` | 198 | 2 Mbaud、DMA 通道、引脚 |
| `Core/Src/fdcan.c` | 157 | 波特率、滤波器、FIFO |

## 6. 第四段：外部接口

### 6.1 `Core/Src/debug_console.c`（1285 行）

| 看什么 | 观察点 |
|---|---|
| 顶部缓冲宏 | `DC_DMA_RX_SIZE`/`DC_RING_SIZE`/`DC_LINE_SIZE`/`DC_MAX_ARGS`/`DC_MAX_VARIABLES`/`DC_MAX_COMMANDS` |
| `DebugConsole_OnRxEvent()` | 中断侧：把 DMA 收到的字节逐个 push 进环形队列，然后重启接收 |
| `DebugConsole_Process()` | 主循环侧：pop 字节 → 组装文本行（CR/LF/CRLF）→ `DC_ParseLine` |
| `DC_ParseLine()` | 内置命令 `help`/`?`/`list`/`get`/`set`，再查用户命令表 |
| 注册接口 | `DebugConsole_RegisterF32/I32/U32/Bool/Command` |
| `DebugConsole_Printf()` | 格式化后用 `motor_console_tx_active` 与波形发送互斥 |

**读完应能回答**：为什么命令解析不在中断里做？

### 6.2 `Core/Src/motor_protocol.c`（627 行）

| 看什么 | 观察点 |
|---|---|
| 帧 ID 与 DLC 宏 | 控制/反馈/心跳/调试/HELLO/Boot |
| `HAL_FDCAN_RxFifo0Callback()` | **中断侧**：RX FIFO0 新报文，把帧搬进 8 深环形队列；队列满时读出并丢弃 |
| `MotorProtocol_Process()` | **主循环侧**：消费队列 → `MotorProtocol_HandleRx()`；另按 1 s 调度心跳 |
| `MotorProtocol_TimerTick()` | **TIM6 1 ms 中断**：推进 10 个时隙；调试独占时按 2 分频发调试帧 |
| 控制命令码处理 | `CMD_SPEED_VECTOR`/`CMD_RUN_VECTOR`/`CMD_DEBUG_SELECT`/`CMD_STATUS_ONCE`/`CMD_ENTER_BOOT` |
| CRC8 | 覆盖范围与参数（注意 24 字节控制帧**不带** CRC） |
| Boot 请求路径 | 写 `TAMP->BKP0R` 魔数 → ACK → `NVIC_SystemReset()` |

> 读这个文件时，**不要**去找 `MotorProtocol_PollRx()` 或 `MotorProtocol_RunScheduler()`：
> 早期文档描述过这两个函数，当前源码已经改成上面这条中断 + 主循环分工。

### 6.3 `Core/Src/app_boot_control.c`（244 行）

**当前状态要注意**：该文件仍在构建源清单中，但 `main()` 调用的是 `motor_protocol.c` 里的 Boot 处理路径。**不要双重消费 FIFO0。**

## 9. 阅读顺序的三个"不要"

1. **不要从 `motor_app.c` 的第一行顺序读到第 1884 行。** 它同时包含常量、结构体、状态机、调试输出和波形发送；顺序读会淹没在细节里。
2. **不要在没读 `controller.h` 之前读 `controller.c`。** 头文件里的并发约定与无扰切换语义，是理解实现的前提。
3. **不要把 `doc/项目.html` 的源码查看器当成编辑器。** 它展示的是**快照**，不会自动追踪后续代码改动。
